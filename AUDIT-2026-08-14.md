## 🔴 CRITICAL — verified by live exploitation

### C1. `GET /config/admin.js` publishes `ADMIN_PASSWORD` in cleartext to anyone
The single most serious finding. `server.js:2190` serves the admin password, unauthenticated, to any caller.

```
$ curl -s http://host/config/admin.js
window.ADMIN_CONFIG = {"email":"admin@valmontpay.com","password":"SuperSecret123!"};
```

Because `ADMIN_PASSWORD` **is** the `X-Admin-Key` value (`lib/admin-auth.js`), this one request defeats the entire guard layer added in the last audit. Verified full chain:

```
$ curl -s .../api/admin/tenants                       -> 401   (guard "works")
$ KEY=$(curl -s .../config/admin.js | grep -o ...)    -> harvested in 1 request
$ curl -H "X-Admin-Key: $KEY" .../api/admin/tenants   -> 200   (guard defeated)
```

With the harvested key I successfully:
- **Injected fake settled money** — `POST /api/transactions` `{"reference":"PWNED-1","amount":999999,"status":"PAID"}` → `200`, and the balance became `999999`.
- **Rotated tenant API secrets and received the fresh valid secret in the response** — full tenant-integration takeover.
- Reached every `/api/admin/*` route, `manual-transaction`, `webhook-debug` POST, and tenant webhook redirection.

**Aggravating factor:** `CORS: *` is set on this route, so **any website in any visitor's browser** can read the password — no network position required.

> The root cause is architectural: an authentication secret is being used as a *client-side comparison value*. The login is entirely client-side (`admin-login.html` compares `password === ADMIN_PASSWORD` in JavaScript), so the password *must* reach the browser for the design to work. **The guard and the login are mutually incompatible.** Fixing this needs a real server-side session (`POST /api/admin/login` → httpOnly cookie), not a patch to this route.

### C2. Recurring-billing (mandate) endpoints have **no authentication at all**
`server.js:319–390`. Four routes, zero middleware — no `requireAdmin`, no `requireTenantAuth`. These operate on saved Paystack `authorization_code`s: reusable tokens that **pull money from a customer's card/MoMo without further consent**. Proven live with a seeded mandate:

```
[1] GET  /api/v1/mandates            -> 200, dumps every mandate:
    authorization_code, customer_email, merchant, amount, bank, status
[2] POST /api/v1/mandates/charge     -> 200 "Mandate charged successfully"
    >>> Paystack charge fired: pesewas=500000 (GHS 5,000) auth=AUTH_VICTIM_MTN
[3] POST /api/v1/mandates/revoke     -> 200 "Mandate revoked successfully"
```

Step 1 hands an attacker the exact `authorization_code` needed for step 2, so this is a **self-contained, anonymous, remote money-theft primitive**. Step 3 is an anonymous denial-of-revenue. This is materially worse than anything in the previous audit, and that audit does not mention mandates at all — the feature appears to have landed after it, inheriting none of its hardening.

Ghana's Data Protection Act 843 / Payment Systems Act 987 obligations around consent make the unauthenticated `revoke` *and* `charge` pair a regulatory exposure, not just a technical one.

## 🟠 HIGH

### H1. `GET /api/transactions` exposes all customer PII, unauthenticated, `CORS: *`
Every reference, **customer email**, amount, channel and status. Any website can read your full sales ledger and customer list from a visitor's browser. The previous audit knowingly accepted this ("the dashboard needs it without auth today") — but the dashboard *already sends* `X-Admin-Key` on other calls, so the stated blocker no longer exists. Combined with C1 the acceptance is no longer defensible.

### H2. Host-header injection into payment links via the `.vercel.app` wildcard
`lib/base-url.js` allowlists the suffix `.vercel.app`. Anyone can register a Vercel project and get a matching hostname:

```
$ curl -H 'X-Forwarded-Host: attacker-phish.vercel.app' -X POST .../api/v1/transaction/initialize
  "pay_url":"http://attacker-phish.vercel.app/pay.html?access_code=ac_510a84..."
```

The gateway mints payment links, and Paystack `callback_url`s, on an attacker-controlled domain — a clean phishing primitive against your own customers. The allowlist was added as the host-injection *fix*; the wildcard reopens it. Pin to exact production hosts and drive previews from `VERCEL_URL` instead.

### H3. No rate limiting anywhere
Zero occurrences of any limiter across the codebase. Unauthenticated and uncapped: payment-link generation, `POST /api/transactions` (`PENDING_MOMO` rows), `/api/log/bad-amount`, and — critically — **admin-key brute force** and mandate enumeration. Each link generation is also a Supabase write, so this is a cost/DoS vector too.

### H4. `/api/tenants` leaks merchant business data publicly
Settlement bank account (`GCB Bank - 1234567890`), webhook URLs, allowed domains, environment, for every tenant. Secrets are correctly withheld (`has_secret_keys: true`), which is good — but settlement account numbers should not be anonymous-readable.

## 🟡 MEDIUM

- **M1. Warn-open auth default.** `isAuthorizedAdmin()` returns `true` when `ADMIN_PASSWORD` is unset. One missing env var in Vercel silently opens every guarded endpoint, with only a log line. Fail *closed* in production (`process.env.VERCEL`).
- **M2. `vercel.json` / `api/*.js` duplication.** `vercel.json` routes `/api/transactions` to `server.js`, so `api/transactions.js` is dead code kept "in lockstep" by hand. Two implementations of a money-writing endpoint with no test asserting equivalence — a drift hazard by construction. Same pattern for webhook-debug, verify-payment, etc.
- **M3. Tests assert no security boundary.** 14 suites and not one asserts "unauthenticated request → 401". Every finding above would have been caught by a dozen lines of test. This is why the last audit's regressions went unnoticed.
- **M4. `uuid@9` moderate CVE** (GHSA-w5hq-g745-h8pq). `uuid` is imported in `server.js` but `uuidv4` appears unused — likely removable outright.
- **M5. `package-lock.json` is gitignored.** No reproducible builds; CI `npm install` can resolve different transitive versions than production. For a payment system, commit the lockfile.
- **M6. Mandates table has RLS enabled but defines no policy** — correct-by-accident (deny-all + service-role bypass), but it should be explicit like `tenants`/`webhook_deliveries` are.
- **M7. Stray `fix.patch`** tracked in the repo root; already-applied README edits. Delete.
- **M8. Webhook replay window is unbounded.** Signature is verified but there is no timestamp/age check. Idempotent upserts blunt the impact, so this is low-severity — but a captured `charge.success` body stays replayable forever.

## 🟢 Verified GOOD — genuinely well done

Credit where due; I tried to break these and could not:

- **Webhook signature verification is correct.** HMAC-SHA512 over the *raw request bytes* (`express.json` `verify` hook), `timingSafeEqual`, length-checked first. Textbook.
- **Amounts are locked server-side.** The public SKU endpoint ignores a caller-supplied price outright — verified: `amount:1` on a GHS 1,400 SKU produced `amount: 1400` and logged `[SKU-LINK] Ignoring caller-supplied amount 1`.
- **No simulated settlement.** The old "free checkout" path is gone; only Paystack can settle. The `charge` endpoint's refusal to self-mark SUCCESS is well-reasoned and well-commented.
- **XSS hygiene is consistently good.** Every `innerHTML` interpolation of server data goes through `escapeHtml`/`esc`. I found no unescaped sink.
- **Reference collisions fixed properly** — `VP-<base36-time>-<8 hex>` from `crypto.randomBytes`. Access codes use 96 bits of CSPRNG entropy.
- **Outbound tenant webhooks are signed** with a per-tenant dedicated secret, and the forwarder *refuses to deliver* rather than send unsigned. Correct failure direction.
- **`scripts/verify-module-graph.mjs`** is an unusually thoughtful piece of ops engineering — it catches the "require()d but never committed" class of bug that fails only on a serverless cold start. Keep it.
- Terminal-status gating on `POST /api/transactions` is the right *idea*, mirrored correctly across both implementations — it's only C1 that undermines it.

## What changed

**C1 — the architectural fix.** `/config/admin.js` is gone (410). Credentials
are now verified only in `POST /api/admin/login`, which returns a 256-bit
random token — stored **hashed** server-side — in an `httpOnly`,
`SameSite=Strict`, `Secure`-in-production cookie. The browser never receives
the password, so XSS cannot read the session and cross-site requests cannot
ride it. `POST /api/admin/logout` invalidates server-side, not just locally.
The `X-Admin-Key` header is retained for CLI/server callers but is no longer
accepted from the query string (logs, history, `Referer`).
*New:* `lib/admin-session.js`.

**C2 — mandates.** All four routes now require admin credentials or a tenant
Bearer key, and `mandateVisibleTo()` enforces ownership on every read, charge
and revoke. Cross-tenant access returns `404`, so the API never confirms
another tenant's `authorization_code` exists. The ownership check runs
*before* any money moves.

**H1** `GET /api/transactions` guarded (both `server.js` and the serverless
twin). **H2** the `.vercel.app` wildcard is removed; legitimate previews now
come from the platform-set `VERCEL_URL`, which a request header cannot forge,
plus an explicit `ADDITIONAL_PUBLIC_HOSTS`. **H3** `lib/rate-limit.js` —
dependency-free, applied to login (5/15min), mandates, link generation,
payment init, order writes and access-code lookups. **H4** `publicTenant()`
returns branding only to anonymous callers.

**M1** fails **closed**: a deployed environment without `ADMIN_PASSWORD` now
returns `503` everywhere instead of silently opening. **M2** the serverless
`api/transactions.js` twin was brought back in lockstep. **M3** the security
suite is the regression net that was missing. **M4** `uuid` was imported but
never used — removed; `npm audit` is now clean. **M5** `package-lock.json` is
tracked and CI uses `npm ci`. **M6** explicit service-role RLS policy on
`mandates`. **M7** `fix.patch` deleted.

## Honest caveats

- **Sessions and rate limits are per-process.** On serverless, a cold start
  logs the operator out (fails safe), and N warm instances mean the effective
  rate limit is N × max. This stops single-source brute force and spam but is
  not a distributed quota — use Supabase/Upstash counters if you need a hard
  global cap.
- **M8 (webhook replay window) is unchanged.** Signatures are verified but
  there is still no timestamp check; idempotent upserts keep the impact low.
- Three existing tests encoded the *old* behaviour (the `.vercel.app`
  wildcard, and `fetch(` before the `adminFetch` rename). They were updated
  deliberately, with comments explaining why — not weakened to pass.

## Remaining gap to a true 10

Not done here, and each is a design change rather than a fix: CSP headers and
Subresource Integrity on the CDN-loaded Tailwind, per-tenant scoping of the
ledger read, distributed session/rate-limit state, and structured audit
